# Ferritron アーキテクチャ設計書

> ステータス: **確定 v1.42**（2026-11-08）／ Ferritron **2.0.0**
> 以降の変更は第17章「改訂履歴」に記録し、バージョンを上げて行う。
> コードネーム: ProjectRvst / 正式名称: **Ferritron**

---

## 1. 概要

Ferritron は、JUCE / iPlug2 に代わる次世代のオーディオプラグインフレームワークである。

### 1.1 解決したい課題（JUCE の限界）

- ライセンスの制約（商用利用に有償ライセンスが必要）
- 古いアーキテクチャに起因する重さと肥大化（特に GUI 層）
- 新しいハードウェア（GPU、多コア CPU）を活かしきれない
- プラグインを更新するたびに DAW の再起動が必要

### 1.2 目標

| # | 目標 |
|---|---|
| G1 | Rust をネイティブ言語とし、C++ / C# / Python など**任意の言語をあとから追加**できる |
| G2 | VST3 / CLAP / AU（+ ARA 拡張、将来 AAX / LV2）に対応する |
| G3 | Windows / macOS / Linux でビルド・動作する |
| G4 | GUI 技術（Web、OpenGL、Direct2D、Slint など）を**いつでも差し替え**られる |
| G5 | GPU ネイティブな音声処理。GPU の弱点を技術で潰し、適用範囲を最大化する。CPU のみの処理にも切り替えられる |
| G6 | DAW を落とさずにプラグインを**ホットリロード**できる（開発時。配布後の更新への応用は将来の拡張） |
| G7 | DAW がマルチコアを活かさなくても、空いているコアで並列処理する |
| G8 | JUCE / iPlug2 よりも軽量かつ高速（小さいバイナリ、ゼロアロケーション、ロックフリー） |
| G9 | プラグインがクラッシュしても DAW を落とさない隔離（サンドボックス）を選べる |
| G10 | 共通のローカライズ機能を標準で提供し、開発者も利用者も言語を登録できる |

### 1.3 設計原則

0. **Simple is best ―― ただし将来性・汎用性・柔軟性は犠牲にしない。** 最上位の原則。「機能を減らす」ことではなく、**少ない概念の組み合わせで多くを実現する**ことをシンプルさと定義する。コアは最小に、拡張ポイントは開いたままにする（詳細は 1.5 / 1.6）。
1. **すべての技術選択は差し替え可能なモジュールにする。** 境界は安定した C ABI とする。
2. **拡張は「問い合わせ」で行う**（CLAP 方式の `get_extension`）。コア ABI は変えない。
3. **オーディオスレッドの安全性は Runtime が強制する。** 開発者の注意力に頼らない。
4. **使わないものはリンクしない。** 機能ごとに Cargo feature で分け、バイナリを小さく保つ。

### 1.4 命名について

「VST」は Steinberg の登録商標であり、対応形式も VST に限らないため、正式名称には使わない。

### 1.5 シンプルさの規則（Simple is best）

Ferritron の複雑さは**コアではなく任意モジュールの側に置く**。プラグイン開発者が最初に触れる部分は、常に最小限であること。

#### コアに入れてよいもの

コアに入れるのは、**すべてのプラグインが必ず使うもの**だけである。

- Format Shim（CLAP / VST3 / AU）
- Runtime（スケジューラ、ホットリロード、状態管理）
- ローカライズ基盤（キーの検索、表示言語の決定）
- `ferritron_abi.h`
- Rust バインディング

それ以外（GPU、各 GUI バックエンド、Rust 以外の言語、隔離 Level 2 / 3、ARA など）はすべて任意モジュールとし、**使わなければ1バイトもリンクされない**。

#### 機能追加の判断基準

新しい機能や選択肢は、次の4つをすべて満たす場合にだけ追加する。

1. **実在する問題を解決するか。** 「将来使うかもしれない」機能はコアに入れず、拡張ポイント（1.6）で受け止められる形にしておく
2. **コアの外に置けるか。** 置けるなら必ずモジュールにする
3. **使わない人のコストはゼロか。** バイナリサイズ、起動時間、API の学習量のいずれも増やさない
4. **効果を数値で示せるか。** 性能に関する機能はベンチマークで裏付ける

#### 設定より既定値

- すべての設定項目に「何も書かなければ正しく動く」既定値を持たせる
- 自動で判断できるものは開発者に書かせない（例: 言語のリアルタイム安全性の Tier は言語から自動で決める）
- 選択肢は「迷ったときの答え」が1つに決まるように絞る

#### やり方は1つ

- 同じことを実現する方法を複数用意しない（IDL は1つ、カーネル言語は1つ、既定の GUI バックエンドは1つ）
- 代替手段は「既定で足りない人のための拡張モジュール」として提供する

#### 最小のプラグイン

設計の健全さの指標として、**最小のプラグインがこれだけで書けること**を維持する。

```toml
# my-plugin.frtx
[plugin]
id   = "com.example.gain"
name = "Gain"

[params]
gain = { type = "float", range = [-60, 12], default = 0, unit = "dB" }
```

```rust
use ferritron::prelude::*;

#[derive(Default)]
struct Gain;

#[ferritron::plugin]
impl Process for Gain {
    fn process(&mut self, ctx: &mut Context) {
        let gain = db_to_gain(ctx.params().gain.value());   // プロジェクトファイルから自動生成された型付きパラメータ
        ctx.io().for_each_sample(|s| *s *= gain);
    }
}
```

（`examples/gain` として実装済み。`#[ferritron::plugin]` は `impl` ブロックに付け、`type Params` の挿入とフォーマットのエクスポートを自動で行う）

パラメータの定義元は **プロジェクトファイル（`<名前>.frtx`）の1か所だけ**である（5.4）。各言語のコード、UI、翻訳キーはここから自動生成される。

### 1.6 拡張ポイント（将来性・汎用性・柔軟性）

シンプルさと柔軟性を両立させるため、**「最小のコア」と「開いた拡張ポイント」を分ける**。将来の機能は、コアを変更せずに拡張ポイントへモジュールを差し込むことで追加する。

#### すべての拡張ポイントは同じ形をしている

新しい概念を増やさないため、拡張ポイントはすべて**同一のパターン**で作る。1つ覚えれば、すべての拡張の書き方がわかる。

```
モジュール = 記述子（ID・バージョン・対応OS・能力）
           + バージョン付き C ABI の関数テーブル
           + get_extension(id) による能力の問い合わせ
           + Runtime のレジストリによる自動発見
```

#### 拡張ポイントの一覧

| 拡張ポイント | 差し込むもの | 現時点の実装 | 将来の例 |
|---|---|---|---|
| **Format Adapter** | プラグイン形式 | CLAP / VST3 / AU | AAX, LV2, ブラウザ向け（WCLAP 等）, 未来の新形式 |
| **Language Host** | 開発言語 | Rust, C++ | C#, Python, Go, Swift, JS, 未来の言語 |
| **View Backend** | GUI 技術 | Web（OS 標準 WebView）, wgpu | OpenGL, Direct2D, Slint, CEF, 未来の GUI 技術 |
| **Compute Backend** | 計算デバイス | CPU（SIMD）, wgpu | Vulkan / Metal 直接, CUDA, **NPU**, 未来のアクセラレータ |
| **Isolation Provider** | 実行の隔離方式 | guarded, process | wasm, リモートマシンでのレンダリング |
| **DSP Node** | 再利用できる処理部品 | 基本ノード群 | サードパーティ製ノード、ノードのマーケット |
| **Protocol Extension** | ホストとの新しいやり取り | CLAP 拡張の対応分 | 新しい DAW の機能、MIDI 2.0 の新仕様 |
| **Locale Provider** | 翻訳の供給元 | 埋め込み, 言語パック（外部ファイル） | 翻訳サービスとの連携、オンライン配信 |
| **Toolchain Plugin** | ビルド・配布の工程 | ビルド, バンドル作成 | コード署名、インストーラ生成、ストア配布 |

**「GPU」ではなく「Compute Backend」と一般化する**のがポイントである。将来 NPU や新しいアクセラレータが登場しても、同じ拡張ポイントに差し込むだけで対応できる。

#### 将来性を守るための規則

1. **コア ABI は長期間変えない。** 変更が必要な機能は、すべて拡張（`*.v1` → `*.v2`）として追加する
2. **拡張 ID は必ずバージョン付き**にする。古い版と新しい版を並存させ、段階的に移行できるようにする
3. **保存データ（プラグインの状態、プリセット）にはバージョンを付け、移行関数を必須にする。** 何年前のプロジェクトファイルでも開けること
4. **非推奨化には猶予期間を設ける。** 少なくとも1つのメジャーバージョンの間は、警告を出しつつ動かし続ける
5. **プラットフォーム依存の処理は必ず抽象化層の内側に閉じ込める。** 新しい OS（iOS、Wayland、ブラウザなど）への対応は、その層の実装を足すだけで済むようにする

#### シンプルさと柔軟性の両立

| 利用者 | 見えるもの |
|---|---|
| 初心者 | 最小のプラグイン（1.5）だけ。既定値で正しく動く |
| 中級者 | マニフェストの設定項目で、GUI・GPU・隔離方式を選べる |
| 上級者 | 拡張ポイントに独自のモジュールを差し込める |
| 拡張開発者 | 1つのパターンで、あらゆる拡張を書ける |

複雑さは、それを必要とする人の前にだけ現れる。

## 2. 全体アーキテクチャ

```
┌──────────────────────── DAW プロセス ─────────────────────────┐
│                                                                │
│  [Format Shim]  MyPlugin.vst3 / .clap / .component  ← 不変・極小 │
│     │  VST3 / CLAP / AU / ARA アダプタ（ホストとの ABI だけを担当）│
│     ▼                                                          │
│  [Ferritron Runtime]  プロセス内で1つだけ共有                    │
│     ├─ Hot-Reload Manager（監視→ステージング→状態移行→差し替え）  │
│     ├─ Scheduler（スレッドプール / Audio Workgroup / MMCSS）     │
│     ├─ Compute Context（GPU 等を全インスタンスで共有・バッチ化）  │
│     ├─ Language Host Loader（言語モジュールの読み込み）           │
│     ├─ Locale（翻訳の検索・表示言語の決定）                       │
│     └─ Param / State / Event バス（ロックフリー）                │
│     ▼                                                          │
│  [Plugin Core]  my_plugin.<hash>.dll  ← ホットスワップ対象       │
│     ferritron_abi.h を実装（Rust / C++ / C# / Python …）         │
│                                                                │
│  [View]  ferritron-view + View Backend                         │
│     Web / GPU / Native Toolkit / Out-of-Process                │
└────────────────────────────────────────────────────────────────┘
```

### 2.1 層の責務

| 層 | 責務 | 更新頻度 |
|---|---|---|
| Format Shim | ホスト固有 ABI の変換のみを担当。ロジックは持たない | ほぼ不変 |
| Runtime | プロセス内で共有する資源（スレッド、計算デバイス、ホットリロード、言語ホスト、ローカライズ） | Ferritron のリリース単位 |
| Plugin Core | 開発者が書く DSP と状態 | 頻繁（ホットリロード対象） |
| View | GUI。DSP とは UI Bridge だけで通信する | 頻繁（UI 側も HMR 可能） |

### 2.2 内部モデルは CLAP 準拠

CLAP は最も新しく、イベント、パラメータ、スレッドモデルが素直である。そのため Ferritron の内部モデルは CLAP に寄せ、VST3 と AU はそのモデルへのアダプタとして実装する（clap-wrapper と同じ発想）。

### 2.3 Runtime のシングルトン化

同じ DAW プロセス内のすべての Ferritron プラグインで Runtime を1つ共有する。

- スレッドプールが1つになり、コア数を超えて過剰にスレッドを作らない
- GPU デバイスが1つになり、インスタンスをまたいでバッチ処理できる
- Runtime のバージョンが違う場合は、バージョンごとに名前空間を分けて共存させる（ABI バージョンで判定）

## 3. プラグイン形式

### 3.1 公式 SDK は開発者が用意する

**Ferritron は各形式の公式 SDK（VST3 SDK、CLAP、AAX SDK など）を同梱しない。** Ferritron が提供するのは、開発者が用意した SDK に対してビルドされる**アダプタ（Format Shim）のみ**である。

- 開発者は SDK の配布元から直接入手し、そのライセンスに同意する（AAX のように NDA が必要なものも同じ扱い）
- アダプタは SDK の場所を `ferritron-build` の規則（D38）で決める：プロジェクトの `[sdk]` の固定バージョン、`sdk.toml` の `source`、環境変数（VST3 なら `VST3_SDK_DIR`）、Ferritron の管理フォルダ。見つからない場合は、探した場所と入手・設定の方法を示すエラーでビルドを止める
- `cargo ferritron sdk fetch` と Editor は、利用者が SDK ごとのライセンスに同意したときだけ、配布元から直接取得する（一括同意はしない。同意は `sdk-consent.toml` に記録）
- リポジトリには SDK のヘッダーや、SDK から書き写したインターフェース定義・IID を含めない
- シムは C ABI（`ferritron_abi.h`）だけを通してプラグイン本体と話すため、SDK に触れるのはシムだけである

```
開発者の SDK ──(include)──▶ Format Shim（C++、Ferritron 提供）──▶ ferritron_abi.h ──▶ Rust コア + プラグイン
```

### 3.2 対応状況

| 形式 | 方針 | 備考 |
|---|---|---|
| CLAP | ネイティブ実装（内部モデル） | MIT |
| VST3 | CLAP モデルへのアダプタ | VST3 SDK は 2025 年に MIT 化 |
| AU v2 | アダプタ | macOS のみ |
| AU v3 / iOS | 将来（Format Adapter として追加） | App Extension のサンドボックスがあり、ホットリロードや GPU に制約 |
| ARA 2 | 形式ではなく**拡張**として実装 | ARA SDK は Apache-2.0 |
| AAX | 将来（Format Adapter として追加） | NDA と Avid の署名が必要 |
| LV2 | 将来（Format Adapter として追加） | Linux 向け |
| Standalone | 開発・テスト用 | オーディオ I/O 付きの単体アプリ |

## 4. コア ABI（`ferritron_abi.h`）

すべての言語、すべての拡張モジュールの唯一の契約である。

### 4.1 安定性のための規則

1. **すべての構造体の先頭に `struct_size` と `abi_version` を置く。** 末尾へのフィールド追加は後方互換とする。
2. **新機能は文字列 ID の拡張として追加する**（例: `ferritron.gpu.v1`、`ferritron.ara.v2`）。`get_extension(id)` が NULL を返したら未対応と見なす。
3. **メモリは確保した側が解放する。** 言語ごとにアロケータが違っても破綻しない。
4. **例外や panic は境界を越えさせない。** すべてエラーコードに変換する。
5. **スレッドの種類（main / audio / worker / gpu）を関数ごとに明記する。**

### 4.2 イメージ

```c
typedef struct ferritron_plugin {
    uint32_t struct_size;
    uint32_t abi_version;
    void*    plugin_data;

    bool  (*init)(const struct ferritron_plugin*, const ferritron_host*);        // [main]
    bool  (*activate)(const struct ferritron_plugin*, double sr,
                      uint32_t min_frames, uint32_t max_frames);                 // [main]
    ferritron_status (*process)(const struct ferritron_plugin*,
                                const ferritron_process*);                       // [audio]
    bool  (*save_state)(const struct ferritron_plugin*, ferritron_ostream*);     // [main]
    bool  (*load_state)(const struct ferritron_plugin*, ferritron_istream*);     // [main]
    const void* (*get_extension)(const struct ferritron_plugin*, const char* id);// [any]
    void  (*destroy)(const struct ferritron_plugin*);                            // [main]
} ferritron_plugin;
```

### 4.3 IDL とバインディングの自動生成

ABI を1つの IDL で定義し、各言語のバインディングを生成する。IDL には **WIT（WebAssembly Interface Types）** を採用する。

```
ferritron.wit
  ├─→ Rust       (crate: ferritron)
  ├─→ C / C++    (ferritron.h / ferritron.hpp)
  ├─→ C#         (NuGet: Ferritron)
  ├─→ Python     (PyPI: ferritron)
  └─→ TypeScript (npm: @ferritron/ui)  ← GUI 側もここから生成
```

- **採用理由**: 多言語向けの生成器と解析器がすでに存在し、隔離 Level 2（Wasm, 8.4）やブラウザ向け形式にもそのままつながる
- **生成の方法**: Wasm 向けは既存の wit-bindgen を使う。ネイティブの C ABI 向けは、wit-parser で WIT を読み込む Ferritron 独自の生成器で生成する（wit-bindgen が出力するのは Wasm Component Model 用の ABI であり、`ferritron_abi.h` とは異なるため）

## 5. 言語拡張アーキテクチャ

### 5.1 言語対応そのものを「モジュール」にする

```
ferritron_abi.h
   │
   ├── 直接実装する言語（C 関数をエクスポートできるもの）
   │     Rust（一級市民）, C++, C, Zig, C#（NativeAOT）, Swift …
   │
   └── Language Host Module（ランタイムが必要な言語）
         ferritron-lang-python.dll  ← CPython を内包し、同じ ABI を実装
         ferritron-lang-dotnet.dll  ← CoreCLR を内包（JIT が必要な場合）
         ferritron-lang-lua.dll     ← 将来の追加例
```

新しい言語に対応するときに必要なのは、**ホストモジュールとバインディング生成器の2つだけ**である。Ferritron 本体は変更しない。

### 5.2 リアルタイム安全性の階層

| Tier | 対象 | 実行場所 |
|---|---|---|
| **A: RT 安全** | Rust, C++, Zig, C#（NativeAOT＋アロケーション禁止） | オーディオスレッドで直接実行 |
| **B: 条件付き** | C#（GC あり）, Swift など | 専用スレッドで1ブロック遅延の非同期実行。遅延分はレイテンシとしてホストに報告する |
| **C: 非 RT** | Python, JS, Lua など | 別スレッドまたは別プロセスで、共有メモリ越しに実行。開発、プロトタイプ、UI ロジック向け |

Tier は**言語から自動で決まる**ため、通常は開発者が書く必要はない。アロケーションしない C# を Tier A として扱いたい場合など、必要なときだけマニフェストで上書きできる。Runtime は Tier を検証し、Tier B / C のコードをオーディオスレッドに載せない。

### 5.3 言語ごとの方針

| 言語 | 方式 |
|---|---|
| Rust | `#[ferritron::plugin]` マクロで形式ごとのエクスポートを自動生成する |
| C++ | ヘッダオンリーの `ferritron.hpp` ＋ CMake / Cargo 連携 |
| C# | NativeAOT の `UnmanagedCallersOnly` で ABI を実装する。オーディオスレッドでのアロケーションを検出するアナライザを提供する |
| Python | ① 開発モード: Tier C として実行。② 将来: `@ferritron.kernel` で書いた DSP を Slang（9.11）へトランスパイルし Tier A 化する |

### 5.4 マニフェスト（プロジェクトファイル `<名前>.ferritroject`）

プラグインの設定はすべて、`Cargo.toml` の隣に置くプロジェクトファイル `<名前>.ferritroject`（中身は TOML。1.1 までの `<名前>.frtx` も読む）1 つに書く。JUCE の `.jucer` に当たり、Ferritron Editor はこのファイルを開く。マクロ・CLI・エディタは `ferritron_manifest::locate` で同じ規則で探す：フォルダに `.ferritroject` か `.frtx` が 1 つならそれ、なければ旧名の `ferritron.toml`、2 つ以上（両方の拡張子が並ぶ場合も）ならエラー。

```toml
[plugin]                     # 必須はこのセクションだけ
id   = "com.example.myreverb"
name = "My Reverb"

[dsp]                        # 省略時は Rust
language = "python"          # ferritron-lang-python を自動で読み込む
# tier   = "C"               # 通常は書かない（言語から自動決定）。上書きが必要なときだけ

[view]                       # 省略時は GUI なし
backend = "web"              # これだけで必要なモジュールがビルドに含まれる（6.3）
entry   = "ui/dist"

[params]                     # パラメータの唯一の定義元 → 全言語・UI・翻訳キーへ自動生成
mix   = { type = "float", range = [0, 1],    default = 0.3 }
decay = { type = "float", range = [0.1, 20], default = 2.0, unit = "s" }

# [isolation] / [gpu] も省略可能（既定値: 8.2 / 9.10）
```

すべてのセクションに既定値があり、`[plugin]` 以外は省略できる。

## 6. GUI アーキテクチャ

### 6.1 UI の「中身」と「描画技術」を分ける

```
┌─────────── DAW が渡す親ウィンドウ (HWND / NSView / X11) ───────────┐
│                                                                  │
│  ferritron-view（全バックエンド共通の土台）                         │
│   ├─ ウィンドウ埋め込み・リサイズ・DPI スケーリング                  │
│   ├─ キーボードとフォーカス管理（DAW とのキー入力の奪い合いを解決）  │
│   ├─ タイマー / アイドル処理                                       │
│   └─ UI Bridge（DSP との唯一の通信路）                             │
│        ├─ パラメータ変更（begin / end gesture 付き）               │
│        ├─ メーター・波形ストリーム（ロックフリーリングバッファ）     │
│        └─ 任意メッセージ（プリセット、ファイル選択など）            │
│                     │                                            │
│     ┌───────────────┼────────────────┬─────────────────┐         │
│     ▼               ▼                ▼                 ▼         │
│ [Web]          [GPU]           [Native Toolkit]  [Out-of-Process]│
│ WebView2       wgpu / OpenGL   Slint / egui      別プロセス GUI   │
│ WKWebView      Vulkan / Metal  iced / vizia      (WPF, Tauri,    │
│ WebKitGTK      Direct2D / D3D                     gpui …)        │
│ (CEF 任意)                                                       │

```

プラグイン開発者のコードは **UI Bridge にしか触れない**。そのため描画技術を差し替えても DSP 側は変更不要である。

### 6.2 View Backend インターフェース

```rust
pub trait ViewBackend {
    fn capabilities(&self) -> ViewCaps;   // 対応 OS、リサイズ可否、GPU 要否など
    fn attach(&mut self, parent: RawWindowHandle, size: Size, scale: f64) -> Result<()>;
    fn detach(&mut self);
    fn set_size(&mut self, size: Size) -> bool;
    fn set_scale(&mut self, scale: f64);
    fn on_idle(&mut self, bridge: &mut UiBridge);
}
```

同じ内容を `ferritron_view_abi.h` として C ABI でも公開し、外部の dylib からバックエンドを追加できるようにする。

### 6.3 差し替えの方法

- **指定する場所はマニフェストの `view.backend` の1か所だけ**とする。ビルド時にリンクするバックエンドは、そこから自動で決まる（使わないバックエンドはリンクしない）
- 既定のバックエンドは **Web** とする（テンプレートの初期状態）
- サードパーティ製のバックエンドは、外部モジュール（dylib）として View Backend 拡張ポイントに追加する

### 6.4 Web バックエンド

Tauri はアプリ全体のイベントループを持つ設計で、親ウィンドウへの埋め込みに向かない。そのため **OS 標準の WebView を直接埋め込む**（wry 相当の薄い層）。

| 課題 | 設計 |
|---|---|
| アセット配信 | `localhost` サーバーは使わない。`ferritron://` カスタムプロトコルでバイナリ埋め込みのアセットを配信する |
| パラメータ同期 | TypeScript SDK `@ferritron/ui` を用意し、パラメータ定義から型付き API を自動生成する |
| 高頻度データ | JSON ではなくバイナリで一括送信する（WebView2 の SharedBuffer など）。UI のフレームレートに間引く |
| 開発体験 | 開発モードでは Vite の dev サーバーに接続し、UI も HMR でホットリロードする |
| WebView2 の注意点 | ユーザーデータフォルダは `%LOCALAPPDATA%\Ferritron\WebView2\<ホストのプログラム名>`（オプションの違うプログラム同士でフォルダを共有すると開けないため）。プロセス内で Environment を共有し、インスタンスの生成時に非同期で起動しておく（12.1） |
| Linux | WebKitGTK の X11 埋め込みは困難なため、Out-of-Process か GPU バックエンドへ自動フォールバックする |
| CEF | 将来、任意の View Backend モジュールとして提供する。重いが挙動が OS 間で一致する |

### 6.5 Out-of-Process バックエンド

自分でイベントループを持つフレームワーク（WPF、Tauri、gpui など）を使うためのバックエンド。GUI を別プロセスで動かし、UI Bridge を共有メモリと IPC で中継する。

別プロセスの起動・監視・通信には、隔離 Level 3（8.5）と**同じ `ferritron-host` の仕組み**を使う。別プロセス化の仕組みは Ferritron 全体で1つだけである。

- 利点: どんなフレームワークでも使える。GUI がクラッシュしても DAW は落ちない
- 課題: macOS ではプロセスをまたぐウィンドウ埋め込みができない。IOSurface 経由のテクスチャ共有で合成する必要がある。Wayland も同様。現状の macOS ではエディタをホストのプロセス内で開く（D33）

## 7. ホットリロード

### 7.1 仕組み

Windows は読み込み中の DLL をロックするため、`.vst3` 本体の上書きは不可能である。そこで **Format Shim（不変）と Plugin Core（差し替え対象）を分離**する。

```
1. 監視対象: plugins/my_plugin.dll（開発者がここに上書きする）
2. 変更検知 → 書き込み完了を待つ（サイズの安定 + 署名 / ハッシュ検証）
3. my_plugin.<hash>.dll として一時ディレクトリへコピーし、それを読み込む（ロック回避）
4. 新 Core を非オーディオスレッドで初期化（activate、アロケーションもここで済ませる）
5. 旧 Core で save_state() → 新 Core で load_state()（スキーマ移行フック付き）
6. オーディオスレッドのブロック境界でアトミックにポインタを差し替える
   （任意で数 ms のクロスフェード。無音にせず更新できる）
7. 旧 Core は参照がなくなった時点でアンロードする
```

### 7.2 互換性の扱い

| 変更内容 | 動作 |
|---|---|
| パラメータ ID・I/O 構成・レイテンシが不変 | 完全なライブ更新 |
| パラメータ一覧の変更 | ホストに再スキャンを要求する（VST3 `restartComponent` / CLAP `rescan`）。反映されないホストではプラグインの再挿入を案内する |
| レイテンシの変更 | ホストへ通知する |
| I/O 構成の変更 | 再挿入が必要 |

### 7.3 用途

**開発時専用として開始する。** エンドユーザー向けの自動アップデートへの応用は、将来 Toolchain Plugin（コード署名の検証を必須とする）として追加できる形にしておく。

## 8. クラッシュ隔離（サンドボックス）

### 8.1 前提

同じプロセス内では「プラグインがクラッシュしても DAW は絶対に落ちない」とは保証できない。不正なメモリアクセスが起きた時点で、DAW と共有しているメモリ空間が壊れている可能性があるためである。真の隔離には **Wasm 化**か**別プロセス化**が必要になる。

そこで、性能と安全性のトレードオフを4段階から選べるようにする。

### 8.2 隔離レベル

| レベル | 方式 | 安全性 | 性能コスト | 主な用途 |
|---|---|---|---|---|
| **0: none** | 素のインプロセス | ✕ | なし | 検証済みのリリース品で最速を求める場合 |
| **1: guarded** | インプロセス＋例外捕捉 | △（ベストエフォート） | ほぼなし | リリースビルドの既定（auto 時） |
| **2: wasm** | インプロセス＋ Wasm サンドボックス | ◎ | CPU 1.2〜2倍程度 | 安全性を重視する配布、サードパーティ製モジュール |
| **3: process** | 別プロセスで実行 | ◎ | IPC のコスト、または＋1ブロックの遅延 | 開発ビルドの既定（auto 時）、不安定なプラグイン |

```toml
# <名前>.frtx（通常は書かない）
[isolation]
mode = "auto"   # auto（既定）| none | guarded | wasm | process
```

**既定は `auto`** とし、開発ビルドでは process、リリースビルドでは guarded を自動で選ぶ。4つのレベルはすべて残すが、必要な人だけが明示的に選ぶ。DAW の利用者も、プラグインごとに設定で上書きできる。

### 8.3 Level 1: guarded（インプロセス・ベストエフォート）

ABI の境界ですべての異常を捕捉し、**そのインスタンスだけを停止扱いにして無音を出力**する。

- **Rust の panic**: `catch_unwind` で境界の内側に閉じ込める
- **C# / Python の例外**: Language Host が捕捉してエラーコードに変換する
- **アクセス違反**: Windows は SEH / Vectored Exception Handler、macOS / Linux はシグナルハンドラで、Plugin Core のアドレス範囲内で起きた例外だけを捕捉する
- **無限ループ・処理落ち**: ウォッチドッグがデッドライン超過を検知し、そのインスタンスをバイパスする

**限界**: ヒープ破損やロックを握ったままのクラッシュは、捕捉しても後から DAW が落ちる可能性がある。

### 8.4 Level 2: wasm（インプロセスの真のサンドボックス）

Plugin Core を WebAssembly にコンパイルし、wasmtime（Cranelift による事前コンパイル）で実行する。

- メモリ空間が完全に分離されるため、不正アクセスは安全に捕捉できる trap になる
- 無限ループは epoch interruption で安全に打ち切れる
- IPC がなく、レイテンシも増えない
- IDL に WIT を採用しているため（4.3）、この方式と自然につながる

**限界**: SIMD は 128bit まで（AVX 不可）のためネイティブより遅い。GPU は Runtime 経由でしか使えない。

### 8.5 Level 3: process（別プロセスによる完全隔離）

```
┌──── DAW プロセス ─────┐             ┌──── ferritron-host プロセス ────┐
│  Format Shim（代理）   │  共有メモリ  │  Ferritron Runtime              │
│   ├ 音声バッファ ──────┼───────────→ │   └ Plugin Core（実体）          │
│   ├ イベント/パラメータ │ ←───────────┼─                                │
│   └ 状態スナップショット│  OS イベント │  View（Out-of-Process GUI）     │
└───────────────────────┘   で同期     └─────────────────────────────────┘
```

- **音声**: 共有メモリのリングバッファで受け渡し、Windows はイベント、macOS はセマフォ、Linux は futex で同期する
- **リアルタイム性**: 子プロセス側のスレッドにも MMCSS を設定し、macOS では Audio Workgroup をプロセス間で共有して参加させる
- **同期方式**
  - **同期（既定）**: 同じブロック内で結果を待つ。レイテンシは増えないが、毎ブロック数十 µs の IPC コストと揺らぎがある。開発ビルドとリリースビルドでレイテンシが変わらないため、既定とする
  - **パイプライン**: 1ブロック遅らせて非同期にする。安定するが、遅延分をレイテンシとして報告する
- **GUI**: 6.5 の Out-of-Process GUI と同じ `ferritron-host` プロセスで動く（仕組みは1つ）

#### クラッシュ時の動作

```
1. ホストプロセスの終了を検知 → シムは即座に無音（またはバイパス）を出力
2. プラグイン画面に「クラッシュしました」と表示
3. ferritron-host を自動で再起動
4. シムが保持していた最新の状態スナップショットを復元
5. 処理を再開（DAW は一度も止まらない）
```

これは**ホットリロード（第7章）と同じ仕組み**である。ホットリロードは「予定された再起動」、クラッシュ復旧は「予定外の再起動」であり、状態の保存・復元と無音での差し替えの部品を共有する。

#### プロセスのまとめ方

| 方針 | 長所 | 短所 |
|---|---|---|
| インスタンスごとに1プロセス | 最も安全 | メモリ消費が多い |
| **プラグインの種類ごとに1プロセス（既定）** | バランスが良い | 同じ種類のインスタンスは巻き添えになる |
| 全部を1プロセス | GPU のバッチ処理やスレッドプールを共有できる | 1つ落ちると全部止まる（DAW は無事） |

### 8.6 補足

- **GPU のクラッシュ**: ドライバのリセット（TDR）で GPU デバイスが失われたら CPU 処理へ自動でフォールバックし、裏で GPU を再初期化する
- **セキュリティ用サンドボックス**: Level 3 では OS の機能でファイルやネットワークへのアクセスも制限できる（macOS の sandbox プロファイル、Windows の AppContainer / Job Object、Linux の seccomp）
- **守れない部分**: Format Shim と DAW 内で動く Runtime の一部がクラッシュすると DAW も落ちる。この部分は極小・Rust 製とし、ファジングで徹底的に検証する

## 9. GPU オーディオ処理

### 9.1 方針: GPU の弱点を技術で潰し、適用範囲を最大化する

「GPU が得意な処理だけを任せる」のではなく、**GPU の弱点そのものを潰し、苦手だった処理も GPU 向きの形に変える**。GPU の弱点は次の3つに集約される。

| 弱点 | 中身 | 対策 |
|---|---|---|
| ① 往復のコスト | CPU → GPU → CPU の転送と同期に毎ブロック数百 µs かかる | 9.3 / 9.5 / 9.6 / 9.7 |
| ② 直列の依存 | IIR フィルタなど、前のサンプルの結果が次の計算に必要 | 9.4 |
| ③ 起動のコスト | 小さな処理を毎回 dispatch すると計算より起動が長い | 9.3 / 9.7 |

参考: 48 kHz・64 サンプルの1ブロックは約 1.33 ms で、OS は GPU の応答時間を保証しない。

### 9.2 ハイブリッドノードグラフ（基盤）

- 各 DSP ノードは `cpu` と `gpu` の実装を持てる（どちらか片方だけでも可）
- **パイプライン実行**: GPU 処理を 1〜N ブロック遅らせて非同期化し、その分をレイテンシとして報告する
- **デッドライン監視**: 間に合わなければそのブロックだけ CPU にフォールバックする
- **インスタンス横断のバッチ化**: 同じプラグインが多数のトラックに挿さっていれば、1回の処理でまとめて計算する
- **自動配置**: `activate` 時に CPU 実装と GPU 実装の両方を実測し、その環境で速いほうに配置する（自動チューニング）

### 9.3 技術1: 常駐カーネル（① ③ を潰す）【実装済み・明示的に選択】

> RTX 3070 で実測し実装した（V2、15.1 の「GPU 処理：残り」）。GPU の一部を待機で使い続けるため、自動では選ばず `IirNode::new_low_latency` で明示的に使う。コンピューターに 1 つまで。

毎ブロック dispatch せず、**GPU 上でカーネルを常駐させ**、共有メモリのリングバッファを監視させる。

- dispatch のコストがなくなり、往復は数十 µs 程度まで短縮できる見込み（要実測）
- Apple Silicon や内蔵 GPU では CPU と GPU のメモリが共通のため、コピーも不要になる
- 外付け GPU でも ReBAR（CPU から GPU メモリを直接参照する機能）があれば同様の効果を得られる
- **注意**: Windows は長時間動作するカーネルを強制終了する（TDR）。カーネルは一定時間ごとに区切って再起動する
- 小さいバッファ（64 サンプル）でも GPU を使える領域が大きく広がる

### 9.4 技術2: IIR フィルタの並列化（② を潰す）

- **並列スキャン**: 線形漸化式（例: `y[n] = a·y[n-1] + x[n]`）は結合則を満たすため、並列プレフィックススキャンでブロック全体を log(N) 段で計算できる
- **状態空間のブロック化**: フィルタを状態空間で表し、行列のべき乗でブロック単位にまとめて計算する
- **適用範囲**: EQ、ローパス、ハイパスなど、線形 IIR はほぼすべて GPU 化できる
- **限界**: 非線形フィードバック（ラダーフィルタの歪みなど）は直列のまま。ボイス単位・チャンネル単位の並列化に留まる

### 9.5 技術3: レイテンシ分割（① を潰す）

処理を「すぐ必要な部分」と「遅れてもよい部分」に分ける。

```
入力 ──┬─→ [CPU] 先頭の短い部分（低レイテンシ）────┐
       └─→ [GPU] 残りの大部分（数ブロック遅れで可）─┴─→ 合算 → 出力
```

- **畳み込み**: IR の先頭パーティションを CPU、残りを GPU で処理する（不均一パーティション畳み込み）。長い IR でもレイテンシはゼロにできる
- **リバーブ全般**: 初期反射は CPU、後部残響は GPU
- 線形時不変（LTI）の処理については、この分割を Runtime が自動化する

### 9.6 技術4: 制御信号だけを GPU で計算する（① を潰す）

音声そのものは CPU で処理し、**重い分析だけを GPU に任せる**。制御信号の1ブロック程度の遅れは先読み（ルックアヘッド）で吸収する。

| 処理 | GPU で計算するもの | CPU で適用するもの |
|---|---|---|
| ダイナミック EQ、マルチバンドコンプ | 帯域ごとのレベル分析 | ゲインの適用 |
| AI ノイズ除去、音源分離 | ニューラルネットによるマスク推定 | マスクの適用 |
| ピッチ補正 | ピッチ検出 | ピッチシフト |
| ディエッサー、トランジェント処理 | 検出 | 適用 |

### 9.7 技術5: グラフ全体を GPU 上に留める（① ③ を潰す）

- 連続するノードを**1つのカーネルに融合**し、1ブロックあたりの往復を1回にする
- DAW はプラグインごとに CPU のバッファで受け渡すため、プラグインをまたぐと往復が発生する
- そこで**コンテナプラグイン「Ferritron Chain」**を提供する。複数の Ferritron モジュールを内部に並べれば、チェーン全体で往復1回になる

### 9.8 技術6: GPU 専用ハードウェアの活用

| ハードウェア | 用途 |
|---|---|
| Tensor コア | ニューラルオーディオ（アンプシミュレーション、ノイズ除去、音源分離、RAVE / DDSP 系の合成） |
| RT コア | 部屋の音響シミュレーション、空間オーディオ、リアルタイムに変化するリバーブ |
| 大容量 VRAM | 巨大な IR、サンプルキャッシュ、FFT の作業領域 |

### 9.9 技術7: オフラインレンダリングでは全部 GPU

DAW のバウンス時はリアルタイム性が不要である。CLAP / VST3 のオフライン処理通知を受けたら、**巨大なブロックですべての処理を GPU に任せ**、書き出しを高速化する。

### 9.10 GPU 活用モード

```toml
[gpu]
policy = "balanced"   # off | balanced | max
```

| モード | 動作 | 想定場面 |
|---|---|---|
| off | CPU のみ | GPU がない環境、トラブル時 |
| balanced（既定） | レイテンシを増やさない範囲で GPU を使う（技術1〜5） | 録音、ライブモニタリング |
| max | 数ブロックのレイテンシを許容し、可能なものはすべて GPU に送る | ミックス、マスタリング |

利用者はプラグインごと、またはグローバルに切り替えられる。

### 9.11 開発者向けの仕組み: 1回書けば CPU でも GPU でも動く

- DSP カーネルを **Slang** で書くと、**CPU 用コードと GPU 用シェーダの両方を生成**する
  - GPU 向け: SPIR-V（Vulkan）/ Metal / HLSL（DX12）/ CUDA
  - CPU 向け: Slang の C++ 出力をコンパイラの自動ベクトル化で SIMD 化する
- 数値精度は fp32 を基本とする。一般向け GPU は fp64 が非常に遅いため、誤差補正付き加算などで fp32 のまま精度を保つ

### 9.12 処理カテゴリ別の GPU 適用範囲

| 処理 | 素朴な GPU 化 | 本設計 |
|---|---|---|
| 畳み込み・リバーブ | ○（遅延あり） | ◎（遅延ゼロ） |
| 加算合成・多ボイスシンセ | ○ | ◎ |
| 物理モデリング・モーダル合成 | ○ | ◎ |
| ニューラルオーディオ | ○ | ◎（Tensor コア） |
| 線形 EQ・フィルタ | ✕ | ○（並列スキャン） |
| ダイナミクス系 | ✕ | ○（分析のみ GPU） |
| スペクトル処理・ピッチ処理 | ○ | ◎ |
| 空間オーディオ・音響シミュレーション | – | ◎（RT コア） |
| 非線形フィードバック（アナログモデリング） | ✕ | △（ボイス並列のみ） |
| オフラインレンダリング | ○ | ◎（全部 GPU） |

純粋に直列かつ非線形な処理だけが CPU に残るが、それらは軽量なものが多く CPU で十分間に合う。

### 9.13 バックエンド

- 初期実装: wgpu（Vulkan / Metal / DX12）。通常の dispatch 方式（9.2）はこれで実装する
- **常駐カーネル（9.3）は wgpu では実現が難しい**（ホストと共有するメモリのポーリングや、カーネルが進み続ける保証がない）。Vulkan / Metal / DX12 を直接使うネイティブバックエンドで実装する
- Tensor コア・RT コアの活用もネイティブバックエンド（必要に応じて CUDA / Metal Performance Shaders）で行う
- カーネル言語: **Slang**（9.11）。wgpu へは SPIR-V などの出力を渡す
- いずれのバックエンドも Compute Backend 拡張ポイント（1.6）のモジュールとして実装し、NPU など将来のデバイスも同じ形で追加する

## 10. マルチコア処理

- プロセス内で共有するワークスティーリング型スレッドプール（ロックフリー）
- **Windows**: MMCSS の "Pro Audio" タスクで優先度を上げる
- **macOS**: ホストの **Audio Workgroup** に参加する（参加しないと Apple Silicon で効率コアに回される）
- **CLAP**: ホストが `thread-pool` 拡張を提供していればそちらを優先する
- 並列化の粒度はボイス単位、チャンネル単位、サブバンド単位など、同期コストに見合うものに限る。小さい処理は並列化しない
- DAW 自身のスレッドと奪い合わないよう、ワーカー数は「論理コア数 − 予約数」を上限にし、負荷に応じて調整する

## 11. ローカライズ（多言語対応）

### 11.1 背景と方針

既存の DTM プラグインの多くは英語のみで、ローカライズされていない。原因は、フレームワーク側に共通の仕組みがなく、開発者が毎回自作しなければならないことにある。

Ferritron は**ローカライズを標準機能として提供**し、開発者が翻訳ファイルを置くだけで多言語対応できるようにする。

- パラメータ名など**ホストに見える文字列**を扱うため、最小限の部分（キーの検索、言語の決定、フォールバック）は**コア**に置く
- 文字の描画（フォント、文字の組版）は View Backend の側に置く

### 11.2 翻訳ファイル

形式は **Fluent（`.ftl`）** を採用する。単純な文字列は単純に書け、複数形や変数の埋め込みが必要になったときも同じ形式のまま対応できる（やり方は1つ、かつ柔軟）。

```
my-plugin/
├── my-plugin.frtx
└── locales/
    ├── en/main.ftl     ← 基準言語（必須）
    ├── ja/main.ftl
    └── de/main.ftl
```

```ftl
# locales/en/main.ftl
param-mix   = Mix
param-decay = Decay
voices      = { $count ->
    [one]   { $count } voice
   *[other] { $count } voices
}
```

```ftl
# locales/ja/main.ftl
param-mix   = ミックス
param-decay = 減衰時間
voices      = { $count } ボイス
```

- `locales/` フォルダがあれば自動で検出する。**マニフェストへの記述は不要**（既定の基準言語は `en`）
- パラメータ名は `param-<パラメータID>` という命名規則で自動的に対応づける
- 翻訳ファイルはビルド時にバイナリへ埋め込む

### 11.3 言語の登録

| 登録する人 | 方法 |
|---|---|
| プラグイン開発者 | `locales/<言語コード>/` に `.ftl` を置く |
| 利用者・コミュニティ | **言語パック**を所定のフォルダに置く。再ビルド不要で新しい言語を追加・上書きできる |

言語パックの置き場所:

| OS | パス |
|---|---|
| Windows | `%APPDATA%\Ferritron\locales\<プラグインID>\<言語コード>.ftl` |
| macOS | `~/Library/Application Support/Ferritron/locales/<プラグインID>/<言語コード>.ftl` |
| Linux | `~/.local/share/ferritron/locales/<プラグインID>/<言語コード>.ftl` |

開発者が対応していない言語でも、コミュニティが翻訳を作って配布できる。

### 11.4 表示言語の決定順

```
1. プラグインごとの利用者設定
2. Ferritron 全体の利用者設定（全 Ferritron プラグインで共有）
3. OS の表示言語
4. フォールバックの連鎖（例: ja-JP → ja → en）
5. それでも見つからなければキーそのものを表示
```

Ferritron 全体の設定は**すべての Ferritron 製プラグインで共有**される。利用者は一度「日本語」を選べば、どのメーカーの Ferritron 製プラグインも日本語で表示される。

### 11.5 ローカライズの対象

| 対象 | 方法 | 注意点 |
|---|---|---|
| パラメータ名・短縮名 | Format Shim がホストへ翻訳済みの名前を渡す | オートメーションは ID で保存されるため、言語を変えてもデータは壊れない |
| 値の表示（列挙値・単位） | `Low` / `High` などの列挙値、単位も翻訳対象 | 小数点の記号（例: ドイツ語はカンマ）も言語に合わせる |
| GUI の文字列 | UI Bridge の `t("key", args)` を全 View Backend 共通で提供 | Web 向けには `@ferritron/ui` で言語切り替えに追従する仕組みを提供 |
| プリセット名・カテゴリ | プリセットのメタデータに翻訳キーを持たせる | |
| Ferritron 自身のメッセージ | クラッシュ通知などは Ferritron が翻訳を同梱する | 英語・日本語から開始し、コミュニティで拡充する |
| プラグイン名 | **既定では翻訳しない** | DAW のプラグイン一覧や検索、プロジェクトの互換性に影響するため |

**実行中の言語切り替え**: パラメータ名が変わるので、ホストへ再スキャンを通知する（CLAP `rescan` / VST3 `restartComponent`）。反映されないホストでは、プラグインを開き直したときに反映される。

### 11.6 文字の描画

| バックエンド | 対応 |
|---|---|
| Web | ブラウザエンジンが処理するため追加作業は不要 |
| GPU / ネイティブ | OS のフォント検索（DirectWrite / CoreText / fontconfig）とフォールバックを共通ライブラリで提供する。日本語・中国語・韓国語の文字、アラビア語などの右から左へ書く言語、複雑な文字の組版にも対応する |

### 11.7 開発者を支援するツール

- **型安全なキー**: 基準言語のファイルから Rust / C# / TypeScript などの定数を自動生成する。キーの打ち間違いはコンパイルエラーになる
- **翻訳漏れの検出**: `ferritron i18n check` で、言語ごとの未翻訳キーを一覧表示する
- **擬似ローカライズ**: `[!! Ḿíx ~~ !!]` のように文字列を長く・読みにくく変換して表示し、文字のはみ出しや翻訳し忘れを見つける（ドイツ語は英語より約3割長くなる）
- **翻訳のホットリロード**: 開発モードでは `.ftl` を保存すると即座に画面へ反映する

### 11.8 リアルタイム安全性

翻訳の検索は**オーディオスレッドでは決して行わない**。値の文字列化などはすべてメインスレッドで行う（CLAP の仕様でもメインスレッドの処理である）。

## 12. パフォーマンス方針

JUCE の DSP 自体は遅くない。Ferritron が差をつけるのは次の点である。

- バイナリサイズ（不要な機能をリンクしない）
- オーディオスレッドでのゼロアロケーション・ロックフリーを Runtime 側で強制
- SIMD の積極的な活用
- GPU とマルチコアの活用
- 軽量な GUI 層

**主張は必ずベンチマークの数値で示す**（JUCE / iPlug2 / nih-plug との比較スイートを Phase 2 で用意する）。

### 12.1 動的パフォーマンス（1.1.0）

- **無音時のスリープ**：入力が無音（-120 dBFS 未満）のまま、出力が続きうる長さ（`Process::tail`）が過ぎると、Runtime は `process` を呼ばずに無音を出す。入力・ノートオン・値の変わったパラメータで同じブロックから再開する。`Tail::Auto`（既定）は入力と出力がともに無音で、押さえたノートがない状態が 2 秒続いたとき。`Tail::Samples(n)` は宣言した長さ（レイテンシを加算）、`Tail::Infinite` は止めない。宣言がどうであれ、出力に音が残っている間は止めない。ホストにも伝える（VST3 の silence flags と tail samples、CLAP の `CLAP_PROCESS_SLEEP` と tail 拡張。ABI 拡張 `ferritron.sleep.v1`）。判定は Runtime が行うので、全形式・全プラグインで同じに働く。
- **音質の切り替え**：`ctx.quality()` は書き出し（オフラインレンダリング）中は `Quality::Best`、演奏・編集中は `Quality::Normal`。VST3 はブロックごとの process mode を渡すので、そのブロックから切り替わる。`[quality]` を書くと組み込みの「音質」スイッチ（自動 / 標準 / 最高）が付き、ユーザーが手動で固定できる。各段階で何を変えるか（オーバーサンプリング、フィルタ長など）はプラグインが決める。
- **エディタの事前起動**：Windows では WebView2 のブラウザプロセスの起動に 300 ms 以上かかる（直前のプロセスの終了と重なると数秒）。最初のインスタンスの生成時に非同期で起動し（ホストのメッセージループで完了するので待たない）、非表示の空のビューで生かしておく。全エディタが 1 つの環境を共有し、表示は約 60〜80 ms。データフォルダはホストのプログラムごとに分ける（オプションの違うプロセスが同じフォルダを使うと WebView2 が開けないため）。
- **起動の短縮**：WebAssembly のゲストはコンパイル結果をディスクに置く（約 190 ms → 約 2 ms）。GPU はまず Vulkan（Apple では Metal）だけを起動する（全バックエンドの起動に数百 ms かかっていた。約 790 ms → 約 400 ms）。

### 12.2 2.0.0 の処理経路

2.0.0 で、1 ブロックの処理は次のように流れる（`crates/ferritron-core/src/abi.rs` の `process` / `process_with`）。測定は `docs/performance.md`。

1. **シムがイベントを集めて並べる。** 形式ごとのシムは、パラメータの点・ノート・MIDI を 1 本の配列にまとめ、`ferritron_sort_events`（`ferritron_events.h`、C / C++ のシム）または `abi::sort_events`（Rust のシム: LV2・AU）で時刻順に並べる。どちらも安定（同じ時刻の順序を保つ）、O(n log n)、並んでいれば 1 回の走査、割り当てなし（作業領域はシムが事前に持つ）。CLAP はホストが時刻順に渡すので並べない。
2. **C ABI v2 で渡す。** `process` は `ferritron_process_data*` を受け取る（`size` で版を見分ける。チャンネル、イベント、エグゼキュータ、出力イベントのバッファ）。
3. **起こすかを決める。** 一括設定（プリセット・状態）を反映し、無音でスリープ中なら、値の変わるイベント・ノート・入力の音がなければ `process` を呼ばない（64 サンプルごとの早期終了）。
4. **区間に分けて呼ぶ。** `[process] automation` に従う。`"control"`（既定）は制御周期（既定 32 サンプル）の先頭で値を反映し、値の変わらない周期をつないで 1 回の `process` にする。`"sample"` は値の変わる点ごとに分け（1.x と同じ）、`"events"` は分けずに `ctx.param_events()` で渡す。平滑化（`smooth`）があるパラメータが動いている間は周期ごとに分け、`ctx.ramp` がサンプルごとの値を出す。区間のノートと MIDI は、ブロックごとのスタック上の未初期化の領域に書いた分だけを渡す（以前は 24 KB を毎ブロック初期化しており、それだけで約 1 µs かかっていた）。
5. **出力イベント。** `ctx.set_param` / `ctx.midi_out` は、呼び出し側（シム）が貸した `out_events` のバッファへ直接書く。インスタンスはバッファを持たない。足りなければ捨てて数える。
6. **組み込みバイパス。** 切り替えの 10 ms はプラグインの出力と、レイテンシ分遅らせた入力をクロスフェードする。入力の写しは `activate` で最大ブロック × チャンネル数を確保する（2.0.0 でインスタンスあたりのメモリが増えた主な理由。`Harness::memory_report`）。完全にバイパス中は `process` を呼ばない。
7. **オーディオスレッドの外。** ワーカー（`Worker`）は Ferritron のスレッドで `params_changed` / `tick` を受け、`[streams]` でエディタへ値を送る。設定（`ferritron::settings`）はプラグイン ID ごとの JSON ファイルで、ロックファイルで複数プロセスの書き込みを調停する。
8. **隔離（`[isolation] mode = "process"`）。** 制御用の共有メモリ（約 33 KB）とは別に、音声用の共有メモリを `activate` のたびに必要なら作り直す（チャンネル数 × 最大ブロック長 × 2〈主バスとサイドチェーン〉）。子プロセスは世代番号で新しい領域を開く。ホストが最大ブロック長を超えて渡したブロックは分割して子へ送る。

DSP 部品（SIMD、フィルタ、FFT など）は `ferritron-dsp` に置き、コアは依存しない（`ferritron::dsp`、feature `dsp`）。

### 15.2 Phase 9 構想：Ferritron Remote Processing Server

> **状態：構想のみ（実装しない）。** 将来実装するときに既存の設計を壊さずに済むよう、方針と拡張点だけを決めておく。コード上の準備は `ferritron_graph::Device` を `#[non_exhaustive]` にしたことのみ（`Remote` を後から足しても破壊的変更にならない）。

#### 目的

重い処理（長い IR の畳み込み、大規模なモーダル合成、機械学習モデルなど）を、LAN でつながった **2 台目の PC** に任せ、DAW を動かす PC の CPU・GPU を空ける。Vienna Ensemble Pro や AudioGridder と同じ用途だが、Ferritron では**プラグイン単位ではなくノード単位**で、しかも**自動配置の選択肢の 1 つ**として扱う。

#### 位置づけ：ノードグラフの 3 つ目のデバイス

```
                ┌──── DAW の PC ─────────────────────────┐         ┌──── 2 台目の PC ─────────────────┐
DAW ── Shim ──→ │ Ferritron Runtime                      │  LAN    │ ferritron-remote（常駐サーバー）  │
                │  └ Graph ─ Node(CPU) ─ Node(GPU) ─ RemoteNode ─┼───────→ │  └ Node の実体（CPU / GPU）      │
                │             ↑ choose() が CPU / GPU / Remote を計測 │ ←─────┼─ 結果（ブロック単位）            │
                └────────────────────────────────────────┘         └──────────────────────────────────┘
```

- リモートは 9.2 のハイブリッドノードグラフにおける **`Device::Remote`** とする。`choose()` が CPU・GPU と同じく計測し、ポリシー（`Off` / `Balanced` / `Max`）で選ぶ。プラグイン開発者のコードは変わらない
- 遅延の扱いは GPU のリアルタイム処理（9.5、`RealtimeIirBank`）と同じ：**固定レイテンシを報告**し、間に合わないブロックはローカルの CPU が肩代わりする（状態を結果と一緒に返送してもらい、そこから続きを計算する）。肩代わりできない重さのノードは、そのブロックを無音にせず直前の出力からクロスフェードで隠す
- オフラインレンダリング（`ferritron.render.v1`）では待てるので、レイテンシなしで全ブロックをリモートで処理できる

#### 構成要素

| 要素 | 役割 |
|---|---|
| `ferritron-remote`（サーバー） | 2 台目の PC で常駐。ノードの実体を読み込み、受け取ったブロックを処理して返す。自分のオーディオデバイスは持たず、**届いたブロックに駆動される**のでクロックのずれ（ドリフト）は起きない |
| `RemoteNode`（クライアント） | `Node` トレイトを実装し、オーディオスレッドでは送受信キューに書く・読むだけ（ロックもメモリ確保もしない）。ネットワーク送受信は専用スレッド |
| 発見とペアリング | mDNS / DNS-SD（`_ferritron._tcp`）で LAN 内のサーバーを見つけ、初回だけユーザーがペアリングを承認する（MCP の 127.0.0.1 ＋トークンと異なり、LAN を越えるので明示的な承認と暗号化が必須） |
| Ferritron Editor | サーバーの一覧・ペアリング・負荷表示の画面を持つ（Phase 8 のコアに `Action` を足すだけで CLI・GUI・MCP に同時に出る） |
| MCP ハブ | サーバーと各ノードの配置・負荷を AI に見せ、移動を提案・実行できるようにする（Phase 6 のハブに統合） |

#### 転送

- **音声**：ブロックごとに UDP（または QUIC のデータグラム）、32 bit float の非圧縮。シーケンス番号とブロック位置を付け、欠けたブロックは再送せずローカルで肩代わりする。48 kHz・ステレオで約 3 Mbps なので、1 GbE なら数十ノードでも余裕がある
- **制御**：パラメータ・係数・状態・ノードの読み込みは信頼性のあるストリーム（QUIC ストリームまたは TCP）。パラメータはブロック位置付きで送り、サンプル単位のオートメーション（D20）を保つ
- **暗号化**：QUIC の TLS、またはペアリング時に交換した鍵で Noise。LAN 内でも平文にしない
- 共有メモリのリング＋イベント（8.5 Level 3）と**同じメッセージ形式**を使い、運ぶ層だけをネットワークに差し替える。別プロセス隔離で確かめた「ブロックを渡して結果を受け取る」プロトコルを流用できる

#### サーバーで動かす中身（安全性）

任意のネイティブコードをネットワーク越しに送って実行することはしない。サーバーで動かせるのは次のどれかに限る。

1. **サーバーにインストール済みの同じプラグイン**（プラグイン ID とバージョン、バイナリのハッシュが一致するもの）
2. **Wasm モジュール**（8.4 の Level 2 サンドボックス内で実行。送ってよい）
3. **Slang カーネル**（9.11。ソースまたは中間表現を送り、サーバー側でコンパイル。GPU 上でしか動かず、ファイルやネットワークに触れない）

#### 状態と復帰

- 正しい値は常に DAW 側が持つ。サーバーはほぼ無状態で、接続のたびに状態（パラメータ・係数・フィルタ状態）を送り直して再開する。DirectLink（Phase 7）と同じく、プロジェクトを開き直しても自動で再接続する
- 切断・サーバーの停止・遅延の悪化を検知したら、ノードを**ローカル（CPU / GPU）に自動で戻す**。復帰したら次の安全な区切りでリモートへ戻す。DAW から見たレイテンシは変えない（報告済みのレイテンシの範囲で切り替える）
- サーバーのクラッシュは 8.5 の「クラッシュ時の動作」と同じ流れで扱う（無音ではなくローカルの肩代わり）

#### 決めずに残す事項

V3（実測）：一般的な 1 GbE / 2.5 GbE / Wi-Fi での往復時間と揺らぎ、何ブロックのレイテンシなら 99.9% のブロックが間に合うか。R2（決定）：QUIC と UDP＋TCP のどちらにするか、サーバーを 1 台に限るか複数台に分散するか。
