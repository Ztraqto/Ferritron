# Ferritron の性能

2.0.0 の計画の X0 で作った測定の記録です。**測っていない改善は「改善」と書きません。** 遅くなったものも書きます。
数字は下に書いた 1 台のマシンのもので、比べるのは同じ日に続けて測った値だけです
（同じマシンでも、日によって絶対値が 3〜5 倍ぶれることがありました）。

## 測り方

```bash
# S1・S2・S6（フレームワークの固定費とオートメーション）
cargo run --release -p ferritron-bench-fx -- --full --json out.json --compare tools/bench/baseline-1.4.0-2026-11-10.json --golden tools/bench/golden
# S3・S4・S5（プラグイン全体。各例の #[ignore] テスト）
cargo test --release -p sine-synth -p multiband-test -p gain bench_s -- --ignored --nocapture
```

- `ferritron-bench-fx`（`tools/bench-fx`）は `ferritron::testing::Harness`（ホストと同じ経路）で 8 パラメータのゲインを回し、
  1 秒ぶんのステレオを処理する時間を測ります。列はブロックあたりの平均・p99・最大（µs）、リアルタイム比、
  `process` の呼び出し回数/ブロック、オーディオスレッドでの割り当て回数（feature `alloc-check` の `AllocGuard`）。
- シナリオ: **s1** 自動化なし、**s2** 8 パラメータに 1 サンプルごとの自動化（4096 点/ブロック）、
  **s3** sine-synth の 16 ボイス、**s4** multiband-test（64 サンプルごとに 1 点）、**s5** gain を 64 インスタンス、**s6** 無音（スリープ）。
  S3〜S5 は `testing::time_blocks`（20 ブロックのウォームアップの後に計測）。
- `--golden DIR`: 出力を保存済みの出力（`tools/bench/golden/` は **1.4.0 の出力**）と比べ、最大誤差と最初に違ったサンプルを出します。
- 1.4.0 の数字は、`main`（1.4.0）の作業ツリーに同じベンチを移植して、2.0.0 の直後に同じマシンで測りました
  （`tools/bench/baseline-1.4.0-2026-11-10.json`）。`tools/bench/baseline-1.4.0.json` は 2026-11-09 の古い測定で、比較には使いません。

Intel Core i7-10700KF（16 論理コア）、Windows 10 Home、電源プランは未確認、release ビルド（`lto = "thin"`、`codegen-units = 1`）。

## 計画の目標（3 章）との対応

- **T1（固定費 ≤ 1.4.0）: 達成。** s1 は 0.29 → 0.25 µs（512）。2.0 の途中で 1.5 µs に悪化していたのを直した（下記）。
- **T2: 呼び出し回数は達成、時間は不可（依頼者の決定、2026-11-10）。** `process` は 512 → 16 回（目標どおり）。時間は 142.3 → 67.2 µs（0.47 倍）で、「自動化なしの 2 倍以内」は未達。
  初回の 119.1 µs から、制御周期ごとに各パラメータの最後の値だけを検索・変換するようにして下げた。残りは 4096 イベントの整列（シムと Harness）と走査。
- **T3: 達成。** シムの整列は O(n log n)・安定・割り当てなし（全形式）。VST3 は 2048 点まで捨てない（testhost で 2000 点）。
- **T4: 達成。** 0.34 → 0.29 µs（512）、呼び出し 0 回。
- **T5: 未達のまま改善。** 952 バイト → 約 1.6 KB（初回は約 5.7 KB）。バイパスのクロスフェード（BC4）の入力の写しを、プロセス共有の 4 個のバッファからフェードの間だけ借りる形にした。5 個以上が同時にフェードするとき、あふれた分はフェードなしで切り替わる。
- **T6: 達成。** 1/52。
- **T7: 達成。** `BiquadX4` はスカラー 4 本の約 4.1 倍（SSE2）、`BiquadX8` は約 8.4 倍（AVX2）、スカラーと 1e-6 以内で一致。
- **T8: 達成。** すべてのシナリオで割り当て 0。
- **T9: 達成（Windows）。** GPU エディタは静止中 0 回/秒、30 Hz・120 Hz の指定どおり。
- S3・S4・S5 は 2.0 の方が 2〜10% 遅い。プラグインごとの処理の前後にフレームワークの手順（バイパス、平滑化、変更検出）が増えたぶんで、
  ブロックあたり 0.1〜0.2 µs。

## 出力の比較（G5）

- s1 は 1.4.0 の出力と完全に一致（最大誤差 0）。
- s2 は最初のサンプルから違う（最大誤差 0.146）。BC1 の制御周期による既知の差: 1.4.0 は点ごとに値を変え、2.0 は 32 サンプルの周期の
  先頭でその周期の値に変える。`[process] automation = "sample"` にすると 1.x と同じ分割になる。

## 分かったこと

- **H1 は実測で確認できた。** 1.4.0 は密な自動化で `process` をブロック長と同じ回数呼ぶ。2.0 の制御周期で 512 → 16 回。
- **ブロックごとの配列の初期化が 1 µs かかっていた。** 区間に渡すノート（512 件）と MIDI（1024 件）の配列、計 24 KB を毎ブロック
  埋めていた（1.4.0 にも同じ配列があったが、2.0 で `catch_unwind` の内側に移って最適化で消えなくなった）。未初期化のまま、書いた分
  だけを渡す形にして s1 を 1.5 → 0.25 µs に戻した。測定値を `rdtsc` で区間ごとに分けて見つけた。
- **出力イベントの内部キュー（6 KB/インスタンス）は要らなかった。** 呼び出し側（シム）が貸すバッファへ直接書く形にした。
- **シムの割り当て。** LV2・AU は Rust の安定ソート（20 件を超えると割り当てる）、LV2 は毎ブロック `Vec` を 3 つ作っていた。AAX は
  `std::stable_sort`（一時バッファを確保しうる）、VST2 は挿入ソート。すべて割り当てなしの共通の整列にした（AAX は SDK がないためビルドしていない）。
- p99 と最大値はマシンの揺らぎを含む。比較は平均と呼び出し回数で行う。

## 監査の修正（f5・f6）で測ったもの: FNG の CPU 描画と GPU の畳み込み

上の表と同じマシンかは、報告に CPU の記録が無いため確かめていません。報告にあるのは、Windows で、GPU が NVIDIA RTX 3070 だったことです。
「前」は修正前のコミット、「後」は報告の時点で作業中だった版です（最後のコミットとは限りません）。

### FNG の CPU 描画（f5、U3・U2 など。前は `7707c35`）

- 測った日: 2026-11-11（f5 の報告）。
- 測り方: 同じプロセスで、前（`7707c35` の FNG を一時の crate に展開したもの）と後を**交互に**測った（1 回は 1 シーン 1 フレーム、15 ラウンド）。
  機械の負荷（Defender と別の作業）が大きく揺れたため、別々の実行の比較は採らなかった。測るための道具はリポジトリに入れていない。

### 不透明度のグループのメモリと速さ（f6、U2。前は `e330ba6`、後は `72b8fd1`）

- 測った日: 報告に記録が無い（f6 の作業中）。

  前は `e330ba6` の `cpu.rs` を別に作った実行ファイル、後は今の実行ファイル。**別のプロセスで**、二つを交互に各 2 回ずつ走らせた
  （f5 と違い、同じプロセスでは並べていない）。メモリは実行中の作業セットを 5 ms ごとに数え、その最大。

### GPU の畳み込み、1024 サンプルのブロック（f6、G5。前は `7707c35`）

- 測り方: `Convolver::new(ir, 256)` のあと、`idle-sleep` の 10 秒（起床の測定）、または 256 サンプルか 1024 サンプルのブロックを
  300 回（1 回ごとに実時間で待つ）。前と後は**別の実行**（同じ日に release で測った。報告に日付の記録は無い）。
- 後は報告の時点で作業中だった版。

| 測定 | 前（`7707c35`） | 後 | メモ |
|---|---|---|---|
| アイドルの CPU 時間（4 秒の窓、2 回） | 0 ms/s、0 ms/s | 0 ms/s、0 ms/s | Windows の CPU 時間の刻みでは差が出ない。1 ms の polling が無くなった効果は、この方法では見えない。 |

### 1024 サンプルの欠落を測り直す（f7 1-1、G5）

- 測り方: 実時間のペースで、1 回ごとに待ってブロックを流し、欠落（`missed_blocks()`）を数える。2 秒（94 回の呼び出し）と 6.4 秒（300 回の呼び出し）。
  測ったのは f7 の作業の時点の版（`max_block` を超えるブロックは全部処理し、初回に警告を出す）。
- 報告には、ウォームアップの有無、測った日、機械の記録が無い。機械は上の表と同じ Windows かどうか未確認。

| 呼び出しのブロック | `max_block` | 欠落（約 2 秒、94 回） | 欠落（6.4 秒、300 回） |
|---|---|---|---|
| 256 | 256 | 0 | 0 |
| 1024 | 256 | 7 | 5 |
| 1024 | 1024 | 0 | 未測定 |

- f6 の 553 は、この測り方では再現しなかった（300 回で 5）。f6 の測り方（ウォームアップの有無、GPU の状態）が違った可能性はあるが、確かめていない。
- `max_block = 256` で 1024 を流すのは契約（`max_block` 以下の呼び出し）の外。`max_block = 1024` にすると、同じペースで欠落は 0（2 秒の測定）。
- 256 のときの欠落は 0 なので、「256 のときの 2 倍以内」という目標は満たさない（未達）。原因は未調査。

## 検証の範囲

- Windows で実行: `cargo test --workspace`、VST3 の検査用ホスト（`ferritron-testhost`）、LV2 の検査用ホスト、スタンドアロン、隔離（実際のクラッシュからの復帰を含む）。
- 公式の検査（2026-11-10）: VST3 `validator` は全 24 例が 537 件合格。`clap-validator` 0.4.1 は 23 例中 21 例が失敗 0
  （残る 2 例は例の意図どおりの挙動。結果表の「公式の検査」）。
- 2.0.0 で未実行: CLAP・VST2 の実際のホストでの実行、DAW。
- AAX: AAX SDK 2.10.0 でビルドのみ（Pro Tools がない）。型確認のみ: macOS、iOS、AU、AUv3。
- `clap-validator` の「非正規化数で 2.7〜3 倍遅い」警告: Harness で同じ入力を流すと 1.22 倍（`examples/gain` の `denormal_input_is_not_slower`）。
- 実行していない CPU 機能: AVX-512、NEON。
