## 2. 今回新しく見つけたもの

### M. 保守

- **M1. Windows の CI が無い（E9 の続き）。** `.github/workflows` は `macos.yml` だけです。検証済みとしている唯一の環境（Windows）で、テストを自動で回すものがありません。
  監査の修正は 172 コミットあり、確認はすべて人（と実装した AI）が手で走らせたものです。SDK が要らないクレート（`ferritron-core`・`-dsp`・`-manifest`・`-macros`）だけでも回せます。
- **M2. C のヘッダと Rust の構造体のずれを見つける仕組みが無い。** ABI は `abi.rs`（Rust）と `ferritron_abi.h`（470 行、手書き）の 2 か所にあります。
  同じ並びを、`ferritron.hpp`（C++）、`bindings/csharp/Ferritron.cs`（C#）、`ferritron-wam/web/guest.js`、`ferritron-wasm` の `lib.rs`（バイトの位置を数字で書いている）も持っています。
  ヘッダに `static_assert` は 1 つもなく、実行時に `struct_size` と `abi_version` を比べるだけです。末尾に足すときに片方だけ直しても、ビルドは通ります。
- **M3. 形式のアダプタにテストが無い。** `#[test]` の数: `ferritron-lv2` 0（`unsafe` 181）、`ferritron-au` 0（186）、`ferritron-standalone` 0（159）、`ferritron-wasm` 0（71）、
  `ferritron-vst3`・`-clap`・`-vst2`・`-aax` 0。これらは検査用ホストと validator を手で走らせて確かめています。`ferritron-core` は 124、`ferritron-dsp` は 78、FNG は 88 です。
- **M4. リントと整形の設定が無い。** `Cargo.toml` に `[workspace.lints]` が無く、`rustfmt.toml` も `clippy.toml` もありません。
  `ferritron-core` には `clippy` の警告が残っています（C7 の「現在の状態」）。警告を 0 にして CI で止める、という基準が置けません。
- **M5. 大きなファイル。** `abi.rs` 3008 行、`vst3_shim.cpp` 2137 行、`ferritron-manifest/src/lib.rs` 1952 行、`ferritron-gpu/src/iir.rs` 1707 行、`clap_shim.c` 1677 行。
  `abi.rs` は ABI の型、インスタンス、`process` の経路、スリープ、状態、テストを 1 つに持ちます。監査の修正の多くがこのファイルに集まり、並行して直すと衝突します。
- **M6. 依存が重い。** `Cargo.lock` は 531 パッケージ。同じクレートの別の版が入っています: `windows` 3 つ、`windows-core` 3 つ、`syn` 3 つ、`toml_edit` 3 つ、`windows-sys`・`toml`・`thiserror`・`hashbrown` など 2 つ。
  外部の依存は `[workspace.dependencies]` に無く、各クレートが版を書いています（`serde_json = "1"` が 11 か所、`cc = "1"` が 11 か所）。版を上げるとき、そろえる場所がありません。
- **M7. 同じ事実を書く文書が多い。** 「何が検証済みか」は README（日本語 1406 行、英語 1478 行）、AGENTS.md、CHANGELOG、`ferritron-2.0-status.md`、`performance.md`、問題の文書 3 つにあります。
  f8 と f9 は、ほぼ文書を結果に合わせるだけの回でした。元になる表を 1 つに決め、ほかはそこを指すと、この作業が減ります。
- **M8. validator が一時フォルダにある。** VST3 の `validator.exe` と `clap-validator.exe` は、前のセッションの一時フォルダにあります（今はまだあります）。指示書がその長い道を直に書いています。
  消えると、次の確認の前に作り直しになります。VST3 の validator は SDK のフォルダには作られていません。
- **M9. 作業フォルダに残っているもの。** 追跡していない `Preview/`、`SampleDeck_Settings.json`、`.claude/` が `git status` に出ます。`target-dsp/`、`target-fng/` は無視されていますが、容量を使います。
  ブランチ `audit-fixes`・`audit-fixes-2` は `ferritron-2.0` に入っています。消すかどうかは持ち主の判断です。

### S. 性能（測っていない）

- **S1. `dsp::Fft` はスカラーの基数 2。** 回転の係数を `tw[k * step]` と飛び飛びに読みます（[fft.rs](../crates/ferritron-dsp/src/fft.rs) の `cfft`）。
  小さい段ほど読む間隔が大きく、キャッシュに乗りにくい形です。`forward` と `inverse` の詰め直しは 1 ビンごとに `%` を使います。
  段ごとに並べた係数の表、基数 4、SIMD（実部と虚部が別の配列なので向いている）で速くできます。
- **S2. `PartitionedConvolver` は均一分割。** 1 ブロックの仕事は「分割の数 × ビンの数」の複素数の積和です。長い応答を小さいブロックで使うと分割の数が増えます
  （48 kHz で 2 秒の応答、ブロック 64 なら 1500 分割）。分割の大きさを段々に大きくする方法（非均一分割）で減らせます。内側の積和は SIMD にできます。
- **S3. AU は `render` のたびにトランスポートの拡張を名前で引く**（[au.rs](../crates/ferritron-au/src/au.rs) の `render`。Q8 と同じ形）。
  エフェクトの入力は、いったん自分のバッファへ引いてから出力へ写します（2 回の写し）。ホストの出力バッファへ直接引けます。**AU は Mac で動かしていないので、直すなら Mac で確かめてから。**
- **S4. ビルドの時間。** `lto = "thin"` と `codegen-units = 1` のリリースビルドで、キャッシュは消してあります。3 体が別々の worktree で作業すると、全体の再ビルドが 3 回走り、`target/` も 3 つできます。

### W. 挙動（コードを読んだだけ）

- **W1. AU: メインスレッドが入力のコールバックを設定している瞬間に `render` が来ると、そのブロックはエラーを返す。**
  `pull` は `callback` と `connection` を `try_lock` で読み、取れないと「接続なし」（`kAudioUnitErr_NoConnection`）を返します（[au.rs](../crates/ferritron-au/src/au.rs) の `pull`）。
  確率は低いですが、起きると 1 ブロック無音になり、ホストにエラーが返ります。待たない受け渡し（`util::Swap` か原子的なポインタ）にすれば起きません。Mac で動かしていません。
- **W2. 開発用バンドルとリリースの違い（H1 の言い直し）。** `--dev` のバンドルで動かして確かめたものが、リリースと同じとは限りません。
  AGENTS.md は開発の手順として `--dev` を勧めています。H1 を直すまでは、「テンポ、サイドチェーン、ストリーム、`on_message`、スリープは `--dev` では動かない」と文書に書くのが安全です。

## 3. 効率を上げる手法

### 実行時

1. **1 サンプルずつのリングを、2 つの区間の写しにする。** 同じ形が 5 か所あります: P4（バイパスの遅延）、Q5（MCP のタップ）、Q7（スタンドアロン）、R4（グラフの遅延補正）、Q2（WebAssembly）。
   「折り返しまで」と「折り返しの後」に分けて `copy_from_slice` を呼ぶと、分岐と `%` が消え、コンパイラが SIMD の写しにします。挙動は変わりません。
2. **名前で引くものを、作るときに 1 回だけ引く。** Q8（LV2）、S3（AU）、P9（CLAP のパラメータ ID）。
3. **動いていないときは何もしない。** Q3・R2（エディタのパラメータの読み直し）、E8（MCP の一覧の比較）。`params_revision` のような番号を先に見ます。番号がすべての経路で増えることが前提です。
4. **ブロックごとの大きな配列を、スタックからインスタンスへ移す。** P6。`performance.md` には、24 KB の配列を埋めるだけで 1 µs かかった記録があります。
5. **平滑化の終わりを早く決める。** P1。`exp` を目標の 1e-9 まで追う必要があるかを決めます（−120 dB は 1e-6）。出力が変わるので、`tools/bench/golden` との差を見て決めます。
6. **FFT を速くする。** S1・S2・R1。`ferritron-dsp` には `bench.rs` があります。先に今の速さを記録します。
7. **変わった所だけ描く。** U1（FNG の CPU 描画のダメージ領域）、R5（アトラスの部分アップロード）。

どれも、**直す前と後を同じプロセスで交互に測る**のが `performance.md` のやり方です（別々の実行は 3〜5 倍ぶれた記録があります）。

### 開発

1. **Windows の CI を足す（M1）。** SDK の要らないクレートのテストだけでも、コアの後戻りを止められます。
2. **ABI のずれをコンパイルで止める（M2）。** ヘッダに大きさの `static_assert` を置き、同じ数字を Rust のテストでも確かめます。片方だけ変えるとビルドが止まります。
3. **validator を固定の場所に置く（M8）。** SDK のフォルダの下に作り、環境変数（例: `FERRITRON_VST3_VALIDATOR`、`FERRITRON_CLAP_VALIDATOR`）で指します。指示書に長い道を書かずに済みます。
4. **validator と検査用ホストを 1 つの命令で回す。** 今は例ごとに手で打っています。24 例を回して件数を表にするスクリプトがあれば、回ごとの確認が同じ形になります。
5. **`[workspace.lints]` を置き、警告を 0 にする（M4）。** その後で CI に `clippy -D warnings` を足します。
6. **外部の依存を `[workspace.dependencies]` に集める（M6）。** `cargo tree -d` で重なりを見て、そろえられるものをそろえます。ビルドの時間と `target/` の大きさが減ります。
7. **`abi.rs` を分ける（M5）。** 型、`process`、スリープ、状態、テストに分けると、並行の修正が衝突しにくくなります。挙動を変えない移動だけの回にします。
8. **「検証済み」の表を 1 つにする（M7）。** `ferritron-2.0-status.md` の 3 章と 4 章を元にし、README・AGENTS.md・CHANGELOG はそこを指します。
9. **worktree で並行するときのビルド（S4）。** 3 体が同じ `CARGO_TARGET_DIR` を使うと、依存のビルドは 1 回で済みます（同時には 1 体しかビルドできません）。
   別々にするなら、終わった worktree の `target/` をすぐ消します。

## 4. 直す順の提案

1. **f10（指示書あり）**: P4・Q5（コア）、Q2・P9・Q8（アダプタ）、M1・M2（CI と ABI の見張り）。挙動を変えず、テストで固定できるもの。
2. **H1・W2**: 開発用バンドルの拡張の転送。まず文書に違いを書き、次に転送を足す。
3. **Q3・R2**: `params_revision` がすべての経路で増えることのテストを書いてから。
4. **P1・P6・S1・S2**: 測ってから。設計の判断が要る。

## 5. 追加の分析（2 回目、同じ日）

1 回目に読んでいなかった所を読みました。番号は 2 章の続きです。**すべてコードを読んだだけで、実行していません。**

### 挙動

- **W3. 隔離した子プロセスの処理スレッドが、ふつうの優先度で動く（中）。**
  `[isolation] mode = "process"` では、ホストのオーディオスレッドが子プロセスの `ferritron-instance-<id>` スレッドの応答を待ちます（[server.rs](../crates/ferritron-core/src/isolation/server.rs)）。
  優先度を上げる `raise_priority`（Windows では MMCSS の "Pro Audio"）を呼んでいるのは、`parallel_for` のワーカーだけです（`parallel.rs` の 1 か所）。
  ほかのアプリが CPU を使っていると、子のスレッドが後回しになり、ホストのオーディオスレッドがその間待ちます。`performance.md` の S7（平均 7.9 µs、p99 13.5 µs）は、負荷のないときの数字です。
  直し方の案: 子の処理スレッドの始めに同じ `raise_priority` を呼ぶ。負荷をかけた状態で p99 と最大を測って比べる。
- **W4. 隔離: 1024 個を超えるパラメータは、何も言わずに届かない（低）。** 共有メモリの表は `MAX_PARAMS = 1024` 個で、クライアントもサーバーも `.min(MAX_PARAMS)` で切ります。
  `ferritron-manifest` に、隔離を使うプラグインのパラメータの数を調べる検査は見当たりません。`repeat` を使う大きなプラグインで当たりえます。ビルドのときにエラーにするのが安全です。
- **W5. ARA: ファイルのサンプルレートがホストと違うと、その区間は無音になる（中）。**
  ブリッジの描画は、`source->getSampleRate() != _sampleRate` の区間を飛ばします（[ferritron_ara.cpp](../crates/ferritron-ara/bridge/ferritron_ara.cpp) の `PlaybackRenderer::render`）。
  44.1 kHz のファイルを 48 kHz のプロジェクトに置くと、音が出ません。エラーも記録もありません。`README.md` にこの制限の説明は見当たりませんでした。
  直し方の案: まず文書に書く。次に、レートの比を `render_stretched` の `ratio` に掛けて渡す（プラグインの側で再標本化する）か、ブリッジで再標本化する。
- **W6. ARA: 音声ファイル全体をメモリに読む。確保に失敗するとホストごと落ちる（中）。**
  `updateCache` は `チャンネル数 × サンプル数` の `float` を 1 度に確保し、ホストの読み取りを同期で呼びます。呼ぶのは `noexcept` の通知の中です。
  1 時間のステレオ（48 kHz）で約 1.4 GB。確保が失敗すると例外が `noexcept` を越え、プロセスが終わります。読み込みの間、ホストのスレッドは止まります。
  直し方の案: 確保を `try` で包み、失敗したらキャッシュなし（無音）にする。大きさの上限を決めて文書に書く。
- **W7. ARA: `max_frames` より長いブロックの区間は、何も言わずに飛ばす（低）。** `count * channels > _scratch.size()` のとき `continue`。ホストが告げた最大より長いブロックを渡すと、その区間が無音になります。
- **W8. AAX: 描画スレッドで `std::vector` が伸びる（中、Pro Tools では未実行）。**
  `RenderAudio` は `events_.push_back` でイベントを足し、`sortScratch_.resize` も呼びます（[aax_shim.cpp](../crates/ferritron-aax/shim/aax_shim.cpp)）。
  `events_` の `reserve` はファイルのどこにもありません。容量を超えるたびに、オーディオスレッドで確保が起きます（AGENTS.md の「アダプタのオーディオの経路で `Vec` を使わない」に反します）。
  また、変わったパラメータごとに、全パラメータのキーを文字列で比べます。
  直し方の案: 作るときに `events_` と `sortScratch_` を上限の大きさで確保し、超えた分は捨てる（VST3 シムと同じ扱い）。
- **W9. MCP のトークンと nonce を、`RandomState`（ハッシュ表の種）から作っている（低〜中）。**
  `tools/ferritron-mcp` の `ensure_token` と `ferritron-core` の `mcp::nonce` は、`std::collections::hash_map::RandomState` のハッシュの出力を乱数として使います。
  標準ライブラリは、これを暗号用の乱数とは保証していません（種は OS の乱数ですが、スレッドごとに 1 度だけ取り、後は 1 ずつ足します。出力は SipHash-1-3 です）。
  トークンは長く使う秘密です。プロジェクトロック（非公開）は `getrandom` を使っているので、同じものを使えます。

### 性能

- **S5. 隔離のサーバーは、毎ブロック全パラメータを読む。** ブロックごとに最大 1024 個の `AtomicU64` を `SeqCst` で読み、前の値と比べます。
  クライアントが「変わった」番号を 1 つ持てば、動いていないときは読まずに済みます。インスタンスごとに、15 ms ごとに起きるスレッド（`poller`）も 1 本ずつあります。
- **S6. GPU の処理スレッドも、ふつうの優先度（仮説）。** W3 と同じ理由で、`ferritron-gpu` の GPU スレッドは優先度を上げていません。
  G5（1024 サンプルのブロックで間に合わない、原因は未調査）の候補の 1 つです。**確かめていません。** 優先度を上げた版と交互に測れば分かります。

### 保守

- **M10. GPU が無いと、GPU のテストは「合格」になる。** `ferritron-gpu` と `ferritron-vulkan` のテストは、GPU が無いとき `eprintln!("skipping: ...")` を出して戻ります（35 か所）。
  結果は「失敗 0」で、走ったかどうかは出力を読まないと分かりません。この機械には GPU（RTX 3070）がありますが、CI や別の機械では、何も確かめないまま通ります。
  飛ばした数を数えて最後に出す、または `FERRITRON_REQUIRE_GPU=1` のときは失敗にする、という形が使えます。
- **M11. `.git/objects/pack` に、対応する `.pack` の無い `.idx` が 6 個ある。** git が命令のたびに警告を出します。`git fsck --connectivity-only` は正常で、履歴は欠けていません。
  6 個の `.idx` を消せば警告は止まります（消していません）。

### 読んで、問題が見つからなかった所
